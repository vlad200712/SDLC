# ADR-0001: Использование гибридного хранения PostgreSQL и SQLite

## Контекст и постановка задачи

Система **AutoService** должна одновременно обеспечивать централизованное многопользовательское хранение данных СТО с защитой от двойного бронирования (`REQ-INT-009`, `REQ-FUNC-014`, `REQ-REL-002`) и автономный просмотр личного гаража и истории ремонтов на мобильном устройстве клиента при отсутствии сети (`REQ-INT-008`, `REQ-FUNC-020`, `REQ-REL-001`, `REQ-PERF-004`).

Какую архитектуру хранения данных выбрать для серверной и клиентской частей, чтобы гарантировать транзакционную целостность расписания боксов и быструю оффлайн-работу сервисной книжки при минимальной сложности синхронизации и нулевой стоимости лицензий?

## Драйверы решения

* **Транзакционная целостность (ACID):** исключение двойной записи в один бокс (`REQ-FUNC-014`, `REQ-REL-002`).
* **Оффлайн-устойчивость клиента:** чтение до 100 записей истории ремонтов за ≤ 200 мс без подключения к Интернету (`REQ-PERF-004`, `REQ-REL-001`).
* **Изоляция данных клиентов:** хранение в локальном кэше только данных авторизованного пользователя (`REQ-DIST-001`).
* **Стоимость и сроки:** бесплатный открытый стек (`REQ-COST-001`) и укладывание в 5 итераций (по итогам Раунда 1 переговоров решено упростить синхронизацию до read-only кэша).
* **Поддержка со стороны Qt 6:** встроенный драйвер `Qt SQL` для локальной БД (`REQ-PORT-001`).

## Рассмотренные варианты

* **Вариант 1:** Гибридная схема PostgreSQL (сервер, мастер-данные) + SQLite (клиент, read-only кэш с односторонней Pull-синхронизацией)
* **Вариант 2:** Гибридная схема PostgreSQL (сервер) + SQLite (клиент) с двусторонней оффлайн-синхронизацией (CRDT / разрешение конфликтов)
* **Вариант 3:** Только серверная БД PostgreSQL с хранением кэша в JSON-файлах на клиенте

## Итог решения

Выбранный вариант: **«Гибридная схема PostgreSQL + SQLite (read-only кэш с односторонней Pull-синхронизацией)»**, потому что он полностью закрывает требования `REQ-INT-008`, `REQ-INT-009`, `REQ-REL-001`, `REQ-REL-002` и `REQ-PERF-004`, при этом сокращает трудоёмкость реализации функции `F10` с 42 ч до 26 ч (экономия 16 ч и \$560 по итогам Раунда 1 переговоров с Заказчиком) без потери пользовательской ценности.

### Последствия

* **Хорошо**, потому что PostgreSQL обеспечивает строгие ACID-транзакции, внешние ключи, JSONB для лога аудита и `SELECT ... FOR UPDATE` при бронировании слотов.
* **Хорошо**, потому что SQLite встроена в `Qt SQL`, поддерживает индексированные запросы за < 50 мс и изолирует данные клиента в локальной таблице.
* **Хорошо**, потому что односторонняя синхронизация (`Pull-only`) исключает сложные конфликты слияния (merge conflicts) при изменении расписания и цен.
* **Плохо**, потому что создание и отмена бронирования невозможны в оффлайн-режиме (клиент получает уведомление о необходимости подключения к сети, что прямо допускается `REQ-REL-001`).

### Подтверждение

Соответствие решению проверяется:
* автоматическими интеграционными тестами `tests/api/test_postgres_persistence.cpp` и `tests/api/test_pg_transaction_rollback.cpp`;
* клиентскими тестами `tests/client/test_sqlite_cache.cpp`, `tests/perf/test_sqlite_read_speed.cpp` (≤ 200 мс на 100 записей);
* инспекцией схемы миграций PostgreSQL и локальной схемы SQLite на код-ревью (`REQ-DIST-001`).

## Плюсы и минусы вариантов

### Вариант 1: PostgreSQL + SQLite (read-only кэш, Pull-only)

Сервер является единственным источником истины; клиент после входа и при восстановлении сети обновляет локальную базу SQLite снимками автомобилей, каталога услуг и завершённых заказов.

* **Хорошо**, потому что гарантирует ACID-целостность расписания и неизменяемость снимков истории (`REQ-FUNC-022`).
* **Хорошо**, потому что сокращает срок разработки синхронизации на 16 часов по сравнению с двусторонним обменом.
* **Нейтрально**, потому что требует очистки локальной БД SQLite при выходе пользователя (`REQ-DIST-001`).
* **Плохо**, потому что пользователь не может поставить запись «в очередь» без Интернета.

### Вариант 2: PostgreSQL + SQLite с двусторонней синхронизацией

Клиент может редактировать данные и создавать черновики бронирований в оффлайне с последующей отправкой и разрешением конфликтов.

* **Хорошо**, потому что позволяет работать на запись в оффлайне.
* **Плохо**, потому что бронирование слота СТО в оффлайне бессмысленно с точки зрения бизнеса (слот к моменту выхода в сеть может быть занят другим клиентом).
* **Плохо**, потому что увеличивает трудоёмкость `F10` до 42 часов и усложняет тестирование.

### Вариант 3: PostgreSQL + плоские JSON-файлы на клиенте

Кэширование ответов сервера в файлах `.json` на устройстве без локальной СУБД.

* **Хорошо**, потому что минимальный объём кода сериализации.
* **Плохо**, потому что не соответствует ограничению `REQ-INT-008` (обязательное использование `SQLite`).
* **Плохо**, потому что при росте истории и фильтрации по автомобилю/пробегу производительность и целостность ниже, чем у индексированной БД SQLite.

## Дополнительная информация

* **Связанные требования SRS:** `REQ-INT-008`, `REQ-INT-009`, `REQ-FUNC-020`, `REQ-FUNC-021`, `REQ-FUNC-022`, `REQ-PERF-004`, `REQ-REL-001`, `REQ-REL-002`, `REQ-DIST-001`, `REQ-COST-001`.
* **Связанные элементы SDD:** `DV-002` (Композиция), `DV-003` (Информационное представление / ER-модель).
* **История согласования:** упрощение до read-only кэша согласовано с Заказчиком в Раунде 1 переговоров (`sdd/negotiations.md`).
* **Условие пересмотра:** появление в будущих версиях (v2.0+) требования к оффлайн-работе мастеров СТО в подземных боксах без Wi-Fi.
