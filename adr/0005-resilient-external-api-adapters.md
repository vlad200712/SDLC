# ADR-0005: Изолированные адаптеры внешних сервисов с таймаутами, повторами и детерминированным fallback

## Контекст и постановка задачи

Система **AutoService** интегрируется с внешними сервисами (`NHTSA VIN API` для декодирования VIN, шлюзы `FCM / APNs` для Push-уведомлений; первоначально также планировался `API курсов валют НБ РБ`, отменённый Заказчиком в Раунде 2 переговоров). Бесплатные и сторонние сервисы могут отвечать с задержкой или возвращать ошибки `5xx`, однако их недоступность не должна блокировать добавление автомобиля или смену статуса заказа (`REQ-INT-004`, `REQ-INT-007`, `REQ-PERF-002`, `REQ-REL-003`).

Как архитектурно организовать интеграцию с внешними HTTP-сервисами, чтобы гарантировать отклик ≤ 3 с и устойчивость основного функционала?

## Драйверы решения

* **Жёсткий таймаут декодирования VIN:** не более 3000 мс с контролируемым возвратом к ручному вводу (`REQ-PERF-002`, `REQ-FUNC-006`).
* **Отказоустойчивость:** до 2 повторных попыток при `5xx` или таймауте и детерминированный запасной сценарий (`REQ-REL-003`).
* **Независимость транзакций БД от внешних вызовов:** смена статуса заказа в PostgreSQL не должна откатываться из-за сбоя Push-шлюза (`REQ-FUNC-019`, `REQ-INT-007`).
* **Наблюдаемость и изоляция изменений:** логирование всех ошибок интеграций с `X-Request-ID` (`REQ-OBS-001`) и лёгкое отключение ненужных сервисов (как произошло с `F13` — API валют в Раунде 2).

## Рассмотренные варианты

* **Вариант 1:** Изолированные серверные адаптеры (паттерн Adapter) с ограниченным таймаутом (≤ 3 с), политикой Retry (до 2 попыток с паузой 300 мс), асинхронной очередью отправки Push и локальным кэшированием декодированных VIN
* **Вариант 2:** Прямые обращения мобильного клиента Qt Quick напрямую к `NHTSA VIN API` без участия сервера Cloud API
* **Вариант 3:** Синхронные вызовы внешних сервисов внутри HTTP-обработчиков и транзакций PostgreSQL без таймаутов и кэширования

## Итог решения

Выбранный вариант: **«Изолированные серверные адаптеры (Adapter + Retry + Fallback + асинхронная очередь Push)»**, потому что он централизует контроль таймаутов (`REQ-PERF-002`), кэширует уже декодированные VIN-номера для снижения нагрузки на NHTSA, защищает транзакции PostgreSQL от сетевых задержек Push-шлюзов и позволяет безболезненно исключить модуль валют (`F13`) после Раунда 2 переговоров.

### Последствия

* **Хорошо**, потому что при недоступности NHTSA клиент через ≤ 3.2 с получает структурированный ответ `fallback_manual: true` и сразу переходит к ручному вводу (`REQ-FUNC-006`).
* **Хорошо**, потому что повторные запросы по популярным WMI/VIN обслуживаются из кэша сервера за < 20 мс.
* **Хорошо**, потому что отказ от `API курсов валют` (`F13`) в Раунде 2 сводится к удалению одного изолированного адаптера без влияния на `PriceCalculator`.
* **Плохо**, потому что добавляется асинхронный фоновый воркер доставки Push-уведомлений (в рамках процесса Cloud API) и таблица очереди событий в PostgreSQL.

### Подтверждение

Соответствие решению проверяется:
* тестами `tests/api/test_nhtsa_vin_integration.cpp`, `tests/perf/test_vin_decode_timeout.cpp` (задержка > 3 с → ответ ≤ 3.2 с);
* тестом `tests/rel/test_external_api_fallback.cpp` (эмуляция `503 Service Unavailable` → 2 повтора → fallback);
* тестом `tests/api/test_push_gateway.cpp` и проверкой логов с `X-Request-ID` (`REQ-OBS-001`).

## Плюсы и минусы вариантов

### Вариант 1: Серверные адаптеры с Retry, кэшем и асинхронным Push

Каждый внешний сервис скрыт за абстрактным C++-интерфейсом (`IVinDecoderAdapter`, `IPushGatewayAdapter`), что облегчает замену провайдера и мокирование в unit-тестах.

* **Хорошо**, потому что гарантирует выполнение `REQ-PERF-002` и `REQ-REL-003`.
* **Хорошо**, потому что упрощает тестирование с помощью mock-адаптеров без доступа к Интернету.
* **Хорошо**, потому что хранит секретные ключи FCM/APNs строго на сервере, а не в мобильном приложении.
* **Плохо**, потому что требует реализации фонового потока/таймера для отправки Push-очереди.

### Вариант 2: Прямые запросы клиента к внешним API

Мобильный клиент самостоятельно запрашивает NHTSA VIN API.

* **Хорошо**, потому что снимает часть исходящего трафика с Cloud API.
* **Плохо**, потому что отсутствует общий кэш VIN между клиентами и централизованное логирование сбоев (`REQ-OBS-001`, `REQ-OBS-002`).
* **Плохо**, потому что изменение формата ответа NHTSA потребует срочного обновления всех установленных мобильных клиентов.

### Вариант 3: Синхронные вызовы внутри транзакций БД

Cloud API вызывает FCM/APNs или NHTSA прямо в теле транзакции PostgreSQL.

* **Хорошо**, потому что минимальное количество классов.
* **Плохо**, потому что зависание внешнего сервиса удерживает соединение из пула PostgreSQL и блокировки строк, приводя к каскадному отказу всего API (`REQ-AVAIL-001`, `REQ-PERF-005`).

## Дополнительная информация

* **Связанные требования SRS:** `REQ-INT-004`, `REQ-INT-007`, `REQ-FUNC-005`, `REQ-FUNC-006`, `REQ-FUNC-019`, `REQ-PERF-002`, `REQ-REL-003`, `REQ-OBS-001`, `REQ-OBS-002`. (Требование `REQ-INT-006` переведено в статус `Dropped` по решению Заказчика в Раунде 2.)
* **Связанные элементы SDD:** `DV-002` (слой `ExternalAdapters`), `DV-004` (контракт `/api/v1/vehicles/decode-vin`), `DV-009` (развёртывание и ресурсы).
* **Условие пересмотра:** рост потока Push-уведомлений свыше 100 сообщений/с (переход с внутренней таблицы очереди на RabbitMQ/Kafka).
