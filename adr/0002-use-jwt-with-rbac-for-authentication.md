# ADR-0002: Применение JWT и серверного RBAC для аутентификации и авторизации

## Контекст и постановка задачи

В системе **AutoService** работают три категории пользователей с принципиально разными полномочиями: Клиент СТО, Мастер СТО и Администратор СТО (`REQ-FUNC-001`–`REQ-FUNC-004`). Необходимо защитить персональные данные клиентов по Закону РБ № 99-З (`REQ-COMP-003`), исключить несанкционированный доступ к чужим автомобилям и панели управления тарифами (`REQ-SEC-004`, `REQ-SEC-010`) и обеспечить безопасное взаимодействие мобильного клиента Qt Quick с сервером Cloud API (`REQ-INT-005`).

Какой механизм аутентификации и разграничения прав доступа выбрать для REST Cloud API, чтобы удовлетворить требованиям безопасности и производительности (`REQ-PERF-001`, p95 ≤ 300 мс)?

## Драйверы решения

* **Серверный контроль доступа (RBAC):** проверка роли и владельца ресурса на каждый запрос (`REQ-SEC-004`, `REQ-SEC-010`).
* **Короткое окно компрометации и отзыв сессий:** access-токен ≤ 30 минут, refresh-токен ≤ 14 дней с отзывом при выходе (`REQ-SEC-003`).
* **Защита от подбора пароля и утечки хешей:** хеширование `Argon2id` / `bcrypt` (cost ≥ 12) и блокировка на 15 минут после 5 неудачных попыток (`REQ-SEC-001`, `REQ-SEC-005`).
* **Производительность API:** минимальные накладные расходы на проверку авторизации (`REQ-PERF-001`, `REQ-PERF-005`).

## Рассмотренные варианты

* **Вариант 1:** Пара JWT (stateless access-токен 30 мин, подпись HS256/RS256) + хранимый в PostgreSQL refresh-токен (14 дн) + серверный middleware RBAC
* **Вариант 2:** Серверные HTTP-сессии (cookie + таблица сессий в PostgreSQL/Redis)
* **Вариант 3:** Внешний провайдер идентификации OAuth 2.0 / OpenID Connect (Keycloak)

## Итог решения

Выбранный вариант: **«Пара JWT (access 30 мин + refresh 14 дн в PostgreSQL) + серверный middleware RBAC»**, потому что он прямо соответствует ограничениям SRS (`REQ-INT-005`, `REQ-SEC-003`, `REQ-SEC-004`), обеспечивает stateless-проверку access-токена без обращения к БД на каждом запросе, поддерживает мгновенный отзыв refresh-токена при выходе и не требует развёртывания отдельного сервиса Keycloak или Redis.

### Последствия

* **Хорошо**, потому что проверка подписи access-токена выполняется в памяти Cloud API за < 1 мс, не перегружая PostgreSQL при 200+ одновременных сессиях (`REQ-PERF-005`).
* **Хорошо**, потому что единый middleware авторизации централизованно проверяет роль (`client`, `master`, `admin`) и привязку `box_id` / `owner_id`, исключая обход ограничений через прямые HTTP-запросы.
* **Хорошо**, потому что хранение хешей refresh-токенов в PostgreSQL позволяет надёжно отзывать сессии при выходе или блокировке мастера администратором (`REQ-FUNC-029`).
* **Плохо**, потому что уже выданный access-токен остаётся действительным до истечения TTL (максимум 30 минут), если не вести дополнительный короткий blacklist для заблокированных сотрудников.

### Подтверждение

Соответствие решению проверяется:
* автоматическими тестами безопасности `tests/sec/test_jwt_ttl_revocation.cpp`, `tests/sec/test_rbac_authorization.cpp`, `tests/sec/test_bruteforce_lockout.cpp`, `tests/sec/test_registration_role_guard.cpp`;
* инспекцией схемы хранения паролей (`Argon2id`) и логов сервера на отсутствие секретов (`REQ-SEC-001`, `REQ-SEC-007`);
* проверкой хранения refresh-токена в защищённом хранилище клиента (`REQ-SEC-009`).

## Плюсы и минусы вариантов

### Вариант 1: JWT (access + refresh в PostgreSQL) + RBAC middleware

Клиент передаёт `Authorization: Bearer <access_jwt>`, а при истечении 30 минут обновляет пару токенов через `/api/v1/auth/refresh` с ротацией refresh-токена.

* **Хорошо**, потому что нативно подходит для мобильного клиента Qt Quick (не зависит от браузерных cookies).
* **Хорошо**, потому что минимизирует количество инфраструктурных компонентов (не нужен Redis).
* **Нейтрально**, потому что требует аккуратного управления секретным ключом подписи через переменные окружения.
* **Плохо**, потому что для мгновенной блокировки уволенного мастера требуется проверка флага активности или короткий TTL (принят компромисс: TTL 15–30 мин + проверка активности для критических операций персонала).

### Вариант 2: Серверные HTTP-сессии в PostgreSQL/Redis

Каждому клиенту выдаётся непрозрачный идентификатор сессии, проверяемый в хранилище на каждом запросе.

* **Хорошо**, потому что позволяет мгновенно отзывать любую сессию.
* **Плохо**, потому что противоречит утверждённому ограничению SRS (`REQ-INT-005`, `REQ-SEC-003` — использование JWT).
* **Плохо**, потому что создаёт дополнительный запрос к БД на каждый вызов API либо требует внедрения Redis.

### Вариант 3: Внешний сервер идентификации Keycloak (OIDC)

Делегирование регистрации, входа и ролей стороннему сервису Keycloak.

* **Хорошо**, потому что предоставляет готовые политики безопасности и MFA.
* **Плохо**, потому что избыточен по ресурсам (JVM, дополнительный контейнер) и срокам настройки для учебного проекта на 10 недель и 3 ролей.

## Дополнительная информация

* **Связанные требования SRS:** `REQ-INT-005`, `REQ-FUNC-001`–`REQ-FUNC-004`, `REQ-FUNC-029`, `REQ-SEC-001`–`REQ-SEC-005`, `REQ-SEC-007`, `REQ-SEC-009`, `REQ-SEC-010`, `REQ-COMP-003`.
* **Связанные элементы SDD:** `DV-002` (AuthModule), `DV-003` (таблицы `users`, `refresh_tokens`), `DV-004` (контракты `/api/v1/auth/*`).
* **Условие пересмотра:** переход к сети из нескольких СТО с единым корпоративным SSO (Active Directory / OIDC).
