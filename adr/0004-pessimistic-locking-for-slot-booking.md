# ADR-0004: Пессимистическая блокировка и уникальный частичный индекс PostgreSQL для защиты от двойного бронирования

## Контекст и постановка задачи

Одной из ключевых функций системы **AutoService** является онлайн-запись на конкретный временной слот рабочего бокса СТО (`REQ-FUNC-013`, `REQ-FUNC-014`). В часы пик два автовладельца могут одновременно отправить запрос на бронирование одного и того же слота одного бокса. Согласно `REQ-FUNC-014` и `REQ-REL-002`, ровно один клиент должен получить `201 Created`, второй – `409 Conflict`, а при сбое на любом шаге все изменения должны откатываться атомарно.

Какой механизм контроля конкурентного доступа применить на сервере Cloud API и в PostgreSQL, чтобы гарантировать отсутствие двойных записей при нагрузке не менее 200 активных сессий (`REQ-PERF-005`) и задержке p95 ≤ 300 мс (`REQ-PERF-001`)?

## Драйверы решения

* **Строгая гарантия отсутствия двойной записи:** 0 пересекающихся активных заказов в одном боксе (`REQ-FUNC-014`).
* **Атомарность бронирования, переноса и отмены:** полный откат при сбое (`REQ-REL-002`, `REQ-FUNC-015`).
* **Производительность при конкурентной нагрузке:** p95 ≤ 300 мс при 200 параллельных клиентах (`REQ-PERF-001`, `REQ-PERF-005`).
* **Масштабируемость сервера:** корректная работа даже при запуске нескольких инстансов `Cloud API`.

## Рассмотренные варианты

* **Вариант 1:** ACID-транзакция PostgreSQL с блокировкой строки бокса (`SELECT ... FOR UPDATE`) + частичный уникальный индекс / исключающее ограничение (`EXCLUDE USING gist`) по интервалу `[slot_start, slot_end)` для активных заказов
* **Вариант 2:** Внутрипроцессный мьютекс (`std::mutex`) в памяти сервера Cloud API
* **Вариант 3:** Оптимистическая блокировка по полю `version` без ограничений на уровне БД

## Итог решения

Выбранный вариант: **«ACID-транзакция PostgreSQL (`SELECT ... FOR UPDATE`) + исключающее ограничение `EXCLUDE USING gist` по активным заказам»**, потому что оно переносит гарантию целостности на уровень СУБД, работает корректно при нескольких экземплярах Cloud API, предотвращает пересечение слотов разной длительности (например, 1 ч и 4.5 ч) и не требует сторонних координаторов блокировок.

### Последствия

* **Хорошо**, потому что даже при ошибке в прикладном коде СУБД физически не позволит вставить два пересекающихся активных заказа в один бокс (`SQLSTATE 23P01` преобразуется сервером в HTTP `409 Conflict`).
* **Хорошо**, потому что при отмене заказа (`status = 'cancelled'`) ограничение перестаёт действовать на отменённую запись, и слот мгновенно освобождается (`REQ-FUNC-015`).
* **Хорошо**, потому что решение обосновывает необходимость 38 часов на `F06` (подтверждено Заказчиком в Раунде 1 переговоров как критический бизнес-риск).
* **Плохо**, потому что требует включения стандартного расширения PostgreSQL `btree_gist` в стартовой SQL-миграции.

### Подтверждение

Соответствие решению проверяется:
* конкурентным нагрузочным тестом `tests/func/test_booking_double_lock.cpp` (10 одновременных запросов на один слот → ровно один `201 Created`, девять `409 Conflict`);
* тестом отката транзакции `tests/rel/test_pg_transaction_rollback.cpp`;
* тестом отмены и переноса за ≥ 2 ч `tests/func/test_booking_cancel_reschedule.cpp`.

## Плюсы и минусы вариантов

### Вариант 1: Транзакция PostgreSQL (`FOR UPDATE` + `EXCLUDE USING gist`)

При создании или переносе заказа транзакция блокирует запись `service_boxes` (`FOR UPDATE`), проверяет правило ≥ 2 ч и длительность, вставляет запись в `orders`; ограничение `EXCLUDE USING gist (box_id WITH =, tstzrange(slot_start, slot_end) WITH &&) WHERE (status <> 'cancelled')` выступает финальной страховкой.

* **Хорошо**, потому что поддерживает заказы произвольной длительности (1 услуга – 1 ч, комплекс из 3 услуг – 4.5 ч).
* **Хорошо**, потому что работает при горизонтальном масштабировании Cloud API.
* **Нейтрально**, потому что требует установки расширения `btree_gist` (входит в стандартный пакет `postgresql-contrib`).
* **Плохо**, потому что создаёт кратковременную сериализацию записей в рамках одного бокса (на 4–10 боксах задержка составляет < 10 мс, что в 30 раз ниже лимита 300 мс).

### Вариант 2: Мьютекс в памяти процесса `Cloud API`

Синхронизация бронирований через `std::mutex` внутри C++-сервера.

* **Хорошо**, потому что просто реализовать для одного процесса.
* **Плохо**, потому что полностью ломается при запуске второго экземпляра сервера или при ручном изменении БД.
* **Плохо**, потому что не защищает данные на уровне схемы БД при сбое процесса.

### Вариант 3: Оптимистическая блокировка по полю `version`

Проверка номера версии расписания при `UPDATE` и повтор при конфликте.

* **Хорошо**, потому что не удерживает блокировки строк в БД.
* **Плохо**, потому что сложнее корректно контролировать пересечение временных интервалов разной длительности без отдельной таблицы агрегатов слотов.
* **Плохо**, потому что при высокой конкуренции на популярный утренний слот приводит к каскаду повторных попыток.

## Дополнительная информация
